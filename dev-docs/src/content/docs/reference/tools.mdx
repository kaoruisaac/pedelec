## `defineTool()`

```ts
function defineTool<
  TArgs = unknown,
  TResult = unknown,
  const TName extends string = string,
>(
  tool: ToolDefinition<TArgs, TResult, TName>,
): ToolDefinition<TArgs, TResult, TName>
```

Returns the provided definition unchanged while preserving TypeScript generics and literal `name` types.

```ts
const updateCounter = defineTool<
  { delta: number },
  { value: number }
>({
  name: "update_counter",
  description: "Update the visible counter by delta.",
  argsSchema: {
    type: "object",
    properties: {
      delta: { type: "integer" },
    },
    required: ["delta"],
  },
  handler: ({ delta }) => ({ value: counter.add(delta) }),
});
```

`defineTool()` itself does not perform validation. Session creation normalizes and validates the tool list.

## `defineDenoModule()`

Vite applications can describe a local or package-backed Deno module using the intended `skills.denoModules` authoring shape:

```ts
import { defineDenoModule } from "@kaoruisaac/pedelec";

const spriteTools = defineDenoModule({
  name: "sprite-tools",
  description: "Sprite authoring and preview utilities.",
  entry: "./agent/sprite-tools.ts",
  usage: `import { previewActorSource } from "sprite-tools";`,
  preferStdinExecution: true,
});

const skills = {
  guidance: "Use the module when sprite preview is needed.",
  tools: [],
  denoModules: [spriteTools],
};
```

`defineDenoModule()` preserves the authoring description while `pedelecVitePlugin()` resolves the `entry`, bundles a self-contained ESM runtime, and rolls up a standalone public declaration artifact during `vite build` and `vite dev`. `createSession()` transfers each prepared artifact and Core materializes an immutable, thread-scoped package plus import map before the session is returned.

Root SDK consumers that never import `@kaoruisaac/pedelec/vite` do not need Vite. The Vite peer is optional. Applications that use the plugin must install a supported Vite 8 release:

```bash
npm install @kaoruisaac/pedelec vite
```

```ts
// vite.config.ts
import { defineConfig } from "vite";
import { pedelecVitePlugin } from "@kaoruisaac/pedelec/vite";

export default defineConfig({
  plugins: [pedelecVitePlugin()],
});
```

The `entry` must be a static string. Relative entries resolve from the source file containing the declaration. Vite string aliases and installed package specifiers, including `package.json` `exports` subpaths, use the application's Vite resolver for runtime bundling and TypeScript bundler resolution for public types. Remote URLs, computed values, inline source, and imported module objects are not supported. Regex-only Vite aliases that TypeScript `paths` cannot express are resolved through the Vite resolver for runtime code; declaration generation follows the same resolved files when Vite can locate them.

The plugin attaches a private, non-enumerable runtime/types artifact on the transformed module object and removes the original authoring `entry` path. It does not write into the application's Pedelec workspace and does not mutate an already-created session.

Keep `usage` concise: it is the common-case agent hint, while the generated declaration bundle is the authoritative surface when an enum or option shape needs inspection.

The Agent imports the logical `name` from a JavaScript/TypeScript script run with `pedelec-deno`. It does not execute the module by its private filesystem path. Host Context lists the name, description, usage example, and a workspace-relative `index.d.ts` pointer for exact API discovery. The generated `index.mjs` is an implementation fallback, not the normal API reference.

`preferStdinExecution` is optional metadata for modules primarily used by short scripts. When `true`, Host Context adds a concrete module-specific `runCommand`, such as `pedelec-deno --thread-id <thread-id> run -`, to steer the Agent toward stdin execution; the raw preference flag is not exposed in the Agent-facing object. It is a preference rather than a restriction: file-backed execution remains valid, and `false` or omission preserves the default behavior. It does not affect bundling or artifact contents.

`entry` supports local relative files, Vite aliases, and installed bare/package `exports` specifiers. It is build-time only; Desktop does not resolve it and runtime npm, JSR, and network fetching are unavailable. Imported modules run with the same restricted Pedelec Deno permissions as the Agent script.

Ending and resuming a session keeps the same module snapshot while Core still knows the thread. `pedelec.resumeSession(sessionId)` reattaches to that snapshot; create a new session to use a rebuilt artifact. `skills.tools` remains a separate App Tool capability: its calls use `pedelec-cli --thread-id ... tool-spec` and `tool-call`, while Deno Modules stay inside the `pedelec-deno` script.

## `ToolDefinition`

```ts
type ToolDefinition<
  TArgs = unknown,
  TResult = unknown,
  TName extends string = string,
> = {
  name: TName;
  description: string;
  argsSchema: ToolArgsSchema;
  timeoutMs?: number;
  handler?: ToolSpecificHandler<TArgs, TResult>;
};
```

| Field | Required | Description |
| --- | --- | --- |
| `name` | Yes | Agent-facing name. Must start with a letter and contain only letters, digits, `_`, `.`, `-`. |
| `description` | Yes | Non-empty explanation of behavior, side effects, and selection criteria. |
| `argsSchema` | Yes | Pedelec Tool Args Schema. Root must be an object. |
| `timeoutMs` | No | Positive integer runtime wait limit. Core default is currently 60 seconds. |
| `handler` | No | Inline browser handler retained by the SDK and not sent to Core. |

Names must be unique within a skills manifest.

## `ToolSpecificHandler`

```ts
type ToolSpecificHandler<TArgs = unknown, TResult = unknown> = (
  args: TArgs,
  ctx: ToolCallContext,
) => TResult | Promise<TResult>;
```

The handler executes in browser page context. Type parameters are compile-time only; validate runtime args.

Return values must be compatible with the bridge's JSON data model.

## `SkillsInput`

```ts
type SkillsInput<
  TTools extends readonly ToolDefinition[] = readonly ToolDefinition[],
> = {
  guidance: string;
  tools: TTools;
  denoModules?: readonly DenoModuleDefinition[];
};
```

```ts
const tools = [getCurrentPage, updateCounter] as const;

const skills = {
  guidance: "Read current state before making changes.",
  tools,
} satisfies SkillsInput<typeof tools>;
```

`guidance` must be a string and `tools` must be an array. `denoModules` is optional; each module requires `name`, `description`, `entry`, and `usage`. `preferStdinExecution` is an optional boolean preference. It is populated with Vite-prepared definitions and is transported automatically during `createSession()`.

## `ToolNameOf`

```ts
type ToolNameOf<TTools extends readonly ToolDefinition[]> = Extract<
  TTools[number]["name"],
  string
>;
```

Extracts the union of tool names from a readonly definitions array.

```ts
const tools = [readPage, updateCounter] as const;
type AppToolName = ToolNameOf<typeof tools>;
// "get_current_page" | "update_counter"
```

`createSession()` uses this type to narrow named `session.onTool()` calls.

## `SerializableToolManifest`

```ts
type SerializableToolManifest = {
  name: string;
  description: string;
  argsSchema: ToolArgsSchema;
  timeoutMs?: number;
};
```

This is the tool shape sent to Core. It deliberately excludes `handler`.

## `SerializableSkillsManifest`

```ts
type SerializableSkillsManifest = {
  guidance: string;
  tools: SerializableToolManifest[];
  denoModules?: Array<{
    name: string;
    description: string;
    usage: string;
    preferStdinExecution?: boolean;
  }>;
};
```

This is the normalized skills metadata sent through the bridge. Prepared runtime and declaration sources are transferred through the internal session setup path; `entry` is not sent to Core.

## Inline handler normalization

During `createSession()`:

1. tool entries are checked;
2. `argsSchema` is cloned through JSON serialization;
3. inline handlers are stored in a browser-side map by name;
4. serializable definitions are sent to Core.

A duplicate tool name rejects with `INVALID_INPUT`.

Legacy `input` shorthand is rejected. Use `argsSchema`.

## Handler resolution

For an incoming tool call:

1. named handler registered on the session;
2. inline handler from the original tool definition;
3. generic fallback handler;
4. SDK-created `TOOL_HANDLER_NOT_FOUND` result.

Handler exceptions become `TOOL_HANDLER_ERROR` results. Failure to deliver the result emits `SUBMIT_TOOL_RESULT_FAILED`.

## Tool Args Schema entry types

The root alias:

```ts
type ToolArgsSchema = ToolArgsObjectSchema;
```

Node union:

```ts
type ToolArgsSchemaNode =
  | ToolArgsStringSchema
  | ToolArgsNumberSchema
  | ToolArgsIntegerSchema
  | ToolArgsBooleanSchema
  | ToolArgsArraySchema
  | ToolArgsObjectSchema
  | ToolArgsOneOfSchema;
```
